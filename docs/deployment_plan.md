# Ver2.0 Web Phase 7 VPS / クラウド公開設計

このドキュメントは、FastAPI Webアプリを将来的に VPS やクラウド環境で外部公開し、販売・継続運用できる状態へ近づけるための設計メモです。今回はコード実装ではなく、現状構成、公開方式、推奨構成、運用・セキュリティ上の注意点を整理します。

既存のローカルPC起動、CUI版、GUI版、Web版の機能は変更しません。外部公開する場合は、必ずテスト環境で検証してから本番環境へ反映してください。

## 1. 現在の構成

現時点の Ver2.0 Web版は、小規模利用・検証を前提としたシンプルな構成です。

| 項目 | 現在の構成 | 補足 |
| --- | --- | --- |
| Webフレームワーク | FastAPI | `src/web_app.py` を Uvicorn で起動する構成です。 |
| データベース | SQLite | 既定では `data/inventory.db` を利用します。 |
| 画面 | HTML / CSS / JavaScript | `templates/` と `static/` で構成されるサーバーサイドHTML中心の画面です。 |
| 起動場所 | ローカルPC | 開発・検証時は `127.0.0.1` または `0.0.0.0` で起動します。 |
| 管理者ログイン | 環境変数によるパスワード設定 | 未設定時は開発用初期値が使われるため、本番公開前に必ず変更します。 |

現在の構成は、まず社内・個人利用で動作確認するには扱いやすい一方、インターネット公開時には HTTPS、リバースプロキシ、サービス常駐化、バックアップ、アクセス制限などを追加する必要があります。

## 2. 公開方式の比較

外部公開には複数の方式があります。検証段階と本番運用では重視する点が異なるため、目的に合わせて選択します。

| 方式 | 主な用途 | メリット | 注意点 |
| --- | --- | --- | --- |
| Cloudflare Tunnel | 検証・デモ・一時公開 | ルーターのポート開放なしでローカルPCのWebアプリを外部から確認できます。HTTPS URLを使いやすく、短時間のテストに向いています。 | 本番運用ではトンネル管理、認証、Cloudflare 側設定、運用監視が必要です。一時URLを長期運用の前提にしないでください。 |
| ngrok | 検証・デモ・一時公開 | セットアップが簡単で、ローカル環境をすぐ外部確認できます。 | 無料枠ではURLや制限が変わる場合があります。長期運用・販売用途では契約条件、認証、ログ、制限を確認してください。 |
| VPS | 小規模本番・独自運用 | Ubuntu + Python + Uvicorn + Nginx + systemd などで、独自ドメインとHTTPSを使った本番構成を組めます。コストと自由度のバランスが良いです。 | OS更新、ファイアウォール、バックアップ、監視、障害対応、セキュリティ対策を自分で運用する必要があります。 |
| Render / Railway などのPaaS | 手軽なクラウド本番・検証 | デプロイ、HTTPS、ログ確認などが比較的簡単です。インフラ管理の負担を減らせます。 | SQLite ファイルの永続化やバックアップ方針に制約がある場合があります。将来的には PostgreSQL などマネージドDBとの組み合わせを検討します。 |

## 3. 推奨構成

段階ごとの推奨構成は次のとおりです。

### 検証段階: Cloudflare Tunnel

- ローカルPCで FastAPI / Uvicorn を `127.0.0.1:8000` などに起動します。
- Cloudflare Tunnel で一時公開URLを発行し、スマートフォンや社外ネットワークから動作確認します。
- 公開前に `QR_INVENTORY_ADMIN_PASSWORD` と `QR_INVENTORY_SESSION_SECRET` を必ず設定します。
- テスト完了後はトンネルを停止し、一時URLを放置しないようにします。

### 小規模本番: VPS + FastAPI + SQLite

- Ubuntu VPS 上に Python 実行環境を用意します。
- FastAPI は Uvicorn でローカルポートに常駐させます。
- Nginx をリバースプロキシとして配置し、外部公開は HTTPS のみ許可します。
- SQLite DB は公開ディレクトリ外の永続ディスクに保存します。
- systemd でアプリを自動起動・再起動できるようにします。
- 定期バックアップと復旧手順を運用ルール化します。

この構成は、利用者数が少なく、同時書き込みが多くない小規模な在庫管理に向いています。

### 将来拡張: VPS / PaaS + PostgreSQL

- 利用会社数、拠点数、同時利用者数、データ量が増える場合は PostgreSQL への移行を検討します。
- VPS 上で PostgreSQL を運用するか、PaaS / クラウドのマネージド PostgreSQL を利用します。
- 会社・拠点ごとのデータ分離、ユーザー認証、権限管理、操作ログなどを追加し、販売向けの運用要件に対応します。

## 4. VPS構成案

小規模本番向けの標準的な VPS 構成案です。

```text
Internet
  |
  | HTTPS / 独自ドメイン
  v
Nginx
  |
  | http://127.0.0.1:8000
  v
Uvicorn + FastAPI
  |
  v
SQLite DB（公開ディレクトリ外）
```

### 構成要素

- Ubuntu
  - LTS版を基本候補にします。
  - セキュリティアップデートを定期的に適用します。
- Python
  - アプリが対応する Python バージョンをインストールします。
  - 仮想環境を作成し、`requirements.txt` から依存ライブラリを導入します。
- Uvicorn
  - FastAPI アプリを `127.0.0.1:8000` などのローカルポートで起動します。
  - 直接インターネットへ公開せず、Nginx 経由でアクセスさせます。
- Nginx
  - リバースプロキシとして HTTPS を終端します。
  - 静的ファイル配信、リクエストサイズ制限、タイムアウト設定も必要に応じて調整します。
- systemd
  - Uvicorn プロセスをサービス化します。
  - サーバー再起動時の自動起動、異常終了時の再起動、環境変数の注入に利用します。
- HTTPS
  - Let’s Encrypt などで TLS証明書を設定します。
  - 管理者ログイン、入出庫、DB復旧などの操作を平文 HTTP で送信しないようにします。
- 独自ドメイン
  - DNSで VPS のIPアドレスへ向けます。
  - 将来的な販売・顧客案内を考えると、IP直打ちではなくドメイン運用を基本にします。

### systemd 設定時の考え方

systemd のサービスファイルでは、少なくとも次の内容を明確にします。

- 作業ディレクトリ
- 仮想環境内の Uvicorn 実行パス
- `QR_INVENTORY_ADMIN_PASSWORD`
- `QR_INVENTORY_SESSION_SECRET`
- `QR_INVENTORY_DB_PATH`
- 実行ユーザー
- 再起動ポリシー

秘密情報を Git 管理ファイルへ直接書かず、サーバー上の環境変数ファイルやシークレット管理の仕組みで扱う方針にします。

## 5. セキュリティ注意

外部公開前に、最低限次の項目を確認してください。

- `admin123` のまま公開しない。
  - 開発用初期値のままインターネットに公開すると、第三者に管理者機能を利用される危険があります。
- 管理者パスワードは環境変数で管理する。
  - `QR_INVENTORY_ADMIN_PASSWORD` に強いパスワードを設定します。
  - ソースコード、README、公開リポジトリ、スクリーンショットに本番パスワードを残さないでください。
- セッション署名用の秘密値を設定する。
  - `QR_INVENTORY_SESSION_SECRET` には長いランダム文字列を設定します。
- DBファイルを公開ディレクトリに置かない。
  - SQLite DB は Nginx のドキュメントルートや静的ファイル配信対象の下に置かないでください。
- バックアップファイルを外部公開しない。
  - `backups/` やダンプファイルを Web から直接取得できる場所に置かないでください。
- HTTPS必須。
  - ログイン、在庫操作、CSV取込、DB復旧などは HTTPS 経由でのみ利用できるようにします。
- 最低限のアクセス制限を行う。
  - 管理者機能はログイン必須にします。
  - 必要に応じて Basic認証、IP制限、VPN、Cloudflare Access などを追加します。
  - SSH は公開鍵認証を基本とし、パスワードログインや不要ポートを無効化します。
- OS・ミドルウェアを更新する。
  - Ubuntu、Python、Nginx、依存ライブラリのセキュリティ更新を定期的に確認します。

## 6. バックアップ方針

SQLite 運用では DBファイルが最重要データです。外部公開・販売を見据える場合、バックアップ取得だけでなく、復旧できることまで確認します。

### SQLite DB定期バックアップ

- 1日1回以上、SQLite DB を定期バックアップします。
- CSV取込、棚卸修正、DB復旧など、データを大きく変更する操作前にも手動または自動でバックアップします。
- バックアップ取得中に書き込みが発生する可能性があるため、可能であれば SQLite の `.backup` 方式やアプリ停止時間帯でのコピーを検討します。

### 復旧手順

- 復旧前に現在の DB を退避します。
- 復旧対象のバックアップファイルを選び、別環境または一時DBとして内容を確認します。
- アプリを停止し、DBファイルをバックアップから差し替えます。
- アプリを起動し、品目一覧、検索、入庫、出庫、管理者ログインなどの基本操作を確認します。
- 復旧作業日時、復旧元ファイル、作業者、理由を記録します。

### バックアップ保存先

- アプリ本体とは別のディレクトリ、別ディスク、または外部ストレージへ保存します。
- VPS 障害に備え、同一サーバー内だけでなく、別サーバーやクラウドストレージにもコピーすることを検討します。
- バックアップ保存先は Web 公開対象にしないでください。

### 世代管理

- 例として、日次7世代、週次4世代、月次12世代などの保存ルールを決めます。
- 古いバックアップを削除する前に、直近のバックアップが正常に作成されていることを確認します。
- ランサムウェアや誤削除に備え、書き込み権限を分けた保存先やオフサイト保管も検討します。

## 7. 将来の販売向け課題

販売・複数顧客運用を行うには、現在の小規模利用向け機能に加えて、次の課題を別フェーズで整理・実装する必要があります。

- ユーザー認証
  - 管理者1種類だけでなく、利用者ごとのログインID、パスワード、パスワードリセットを検討します。
- 会社 / 拠点ごとのデータ分離
  - 会社ID、拠点ID、テナントIDなどを設計し、他社・他拠点のデータが見えないようにします。
- PostgreSQL移行
  - 同時利用、データ量増加、バックアップ、監査、将来のクラウド運用を考えると PostgreSQL 対応が重要です。
- 操作ログ
  - 誰が、いつ、どの品目に対して、どの操作を行ったかを追跡できるようにします。
- 権限管理
  - 閲覧のみ、入出庫操作、品目マスタ編集、DB復旧、管理者設定などの権限を分けます。
- 利用規約・免責
  - 在庫差異、データ消失、障害、保守範囲、サポート範囲、責任範囲を文書化します。
- ライセンス整理
  - 利用しているライブラリ、テンプレート、フォント、アイコンなどのライセンスを確認し、販売形態に問題がないか整理します。
